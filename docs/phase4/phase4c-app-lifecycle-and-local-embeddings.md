# Phase 4C — Corpus management and encrypted local embedding-index foundation

## Purpose

Phase 4C connects the Phase 4A/4B trust and retrieval contracts to the application and adds a bounded, encrypted index-construction path for a future on-device embedding model. It does not ship a model or activate dense retrieval.

## Application lifecycle integration

The app exposes a Corpus-management destination and uses Android's Storage Access Framework to let the user select a signed keyring archive or corpus-pack archive. The UI presents publisher root configuration state, keyring version, pack status inventory and the latest startup revalidation result. Import and update remain explicit user actions; destructive removal requires a separate confirmation.

A publisher root is not generated by the app. It must be explicitly reviewed and supplied through build properties. If no valid pinned root is configured, keyring/pack trust operations remain unavailable; the app must not treat an absent root as an instruction to quarantine all previously installed content.

After startup revalidation, a keyring update, pack import/update, or pack removal, dense generations for any non-`INSTALLED` pack version are removed. Only a verified active pack can be selected for embedding.

## Local embedding contract

`LocalTextEmbeddingModel` is a local-only contract. It carries an artifact identity/hash, model ID/version, output dimension and maximum input length. Implementations are expected to run on-device and must not access network services.

`EmbeddingPassageSource` streams immutable original passage text from a signed, validated Corpus Pack index in row-ID order. It does not expose mutable or normalized search text as a quotation.

`LocalEmbeddingIndexBuilder`:

1. Requires the requested pack status to be `INSTALLED` and a non-empty validated index file.
2. Requests bounded passage batches from the source.
3. Checks cursor progress, row ordering, stable evidence key format, input size and embedding output shape.
4. Uses symmetric int8 quantization over L2-normalized vectors.
5. Writes a staging generation through `DenseEmbeddingIndexStore`.
6. Activates the generation only after all rows have been processed successfully.
7. Aborts staging under a non-cancellable cleanup context on errors or cancellation.

## Encrypted storage

Dense vector rows are stored in the existing SQLCipher-encrypted Room database. No plaintext vector sidecar is used and the vector table does not store passage text. Room schema v5 adds generation metadata and vector rows with an index on generation/evidence identity and a foreign-key cascade.

Budgets:

- Batch size defaults to 24; maximum 64.
- One generation: maximum 128 MiB encoded vector payload.
- Total active and staging payload: maximum 256 MiB.
- The builder and Room store enforce the same per-generation limit.

Generation activation, retirement of the previous active generation and cleanup of retired vectors are performed transactionally. Abandoned staging generations are recovered/removed at app initialization. A failed or cancelled build must not replace the last known active generation.

## Retrieval policy

FTS5/BM25 remains the active lexical retriever. The dense store and builder do not by themselves constitute a dense retrieval channel. No synthetic vectors, default embedder or remote fallback may be used. Dense ranking can only be activated after Phase 5 provisions a reviewed, compatible on-device model and its inference/runtime tests pass. Any future hybrid channel must retain hard source-license, scholarly-review, language, madhhab and citation identity filters before ranking/fusion.
